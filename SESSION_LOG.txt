  - aura_engine.py — Claude calls via direct REST (urllib) instead of the

  - static/index.html, static/style.css, static/app.js — vanilla JS frontend

TURN 10
--------------------------------------------------------------------------------
USER:
"I want you to modify the project. Add eligibility rules on which you are
verifying verdict. Add rules on which rationale is checked"

CLAUDE:
Rebuilt appetite_rules.json as a list of named, typed rules (id, type,
severity) instead of scattered if-statements, and rewrote check_appetite()
in aura_engine.py as a small generic rules engine dispatching on rule type.
Added two new rules (MIN_ANNUAL_REVENUE, NON_RENEWED_FOR_CAUSE) — and while
adding the latter, caught another subtle bug: a naive "for cause" substring
check would have also matched the phrase "not for cause" in sample 1; fixed
with an exclude_keywords mechanism.

Built a second, independent module, rationale_rules.py, that runs after
Claude's risk assessment and checks the rationale itself (not the verdict):
minimum length, tier-consistency with the appetite status (e.g. an Ineligible
account can never be tagged "Low risk"), whether flagged data gaps cover
extraction's missing fields, whether every dollar figure Claude cites traces
back to the actual extracted data (a hallucination check), and whether the
rationale actually addresses every triggered eligibility rule.

Wired both into server.py and the UI (rule IDs shown inline; new "Rationale
Verification" checklist panel). Verified all 4 samples still produce correct
outcomes, and ran a synthetic bad-output test through rationale_rules.py to
confirm it correctly catches injected defects (it caught all 5).

verified GET and POST requests both worked correctly through the resulting
public URL. Delivered the URL along with explicit caveats: no
authentication on the tunnel, safe for now because the app is in demo mode,
and a warning not to leave it running with a live API key unattended.
